# HardcoreWorldReset for Minecraft 26.3

## Build and automated verification

Requires a complete Java 25 JDK. The checked-in wrapper downloads Gradle 9.5.1.
Fabric Loader 0.19.5, Loom 1.17.20, and Fabric API 0.166.0+26.3 are used.

```sh
bash gradlew clean build
# Only pass this property after accepting the Minecraft EULA:
bash gradlew -PgameTests -PacceptMinecraftEula=true runGameTest runResetIntegration
```

The distributable is `build/libs/hardcoreworldreset-26.3-1.0.3.jar`.
The sources JAR is not a playable mod. Test classes are excluded from the mod JAR.
GitHub Actions runs the build and both test suites and uploads JARs and logs.
The workflow itself must finish on GitHub before its hosted status is considered verified.

GameTests cover accessor application, inventory/ender chest/experience/statistics/
hunger reset, fire/freezing state, and simultaneous deaths followed by countdown
cancellation. Tests use real ServerPlayer objects with embedded connections because
Minecraft's mock player overrides gameMode() to always return Creative.

`runResetIntegration` creates a fresh disposable server under
`build/run/resetIntegration`, binds to localhost, and exercises two connected
players, death detection, limbo round trips, same/new seeds, attempt counting,
offline inventory/statistics, and reconnecting from limbo. It fails if the test
server exits without writing its success marker. It deletes only its own previous
test directory. Never point destructive testing at a production world.

## Behavior and architecture

Death starts a shared five-second countdown and temporarily puts dead players in
spectator mode. Cancelling restores their original modes. Simultaneous deaths
share one reset. `/hwr` retains on/off, stopCountdown, startTimer, timeRemaining,
reuseSameSeed, and alwaysShowActionBar commands; configuration toggles are saved.
Timers use long arithmetic to avoid overflowing at large minute values. Scheduled
resets repeat until cancelled. Active countdowns/timers are session state and do
not resume after restarting the server.

All connected players must reach limbo before world erasure. Missing limbo aborts
the reset. A partial teleport failure returns players to the overworld and restores
modes without erasing worlds. Reset completion and limbo reconnect recovery share
the same inventory, progression, respawn, and safe teleport path. Online statistics
are cleared in memory, and cached offline statistics/advancements are evicted so
reconnecting cannot restore deleted progress.

Only the overworld, Nether, and End are regenerated. Limbo and other mods'
dimensions are retained. Attempt counts persist in `hardcore_state.txt`.
Spawn search is bounded to nearby chunks; when no safe ground is found, a stone
platform with two air blocks provides a safe fallback instead of spawning over
water or the void. A reset may still pause the server during synchronous chunk
saving and generation.

The unnecessary global registry-lifecycle override has been removed. Vanilla and
Fabric registry validation now run normally. The optional reflective Trinkets
inventory cleanup remains conditional on that mod being loaded, and logs a useful
error if its API differs. No compatible Trinkets installation has been validated.

## Interrupted resets and world safety

Back up worlds before using a destructive reset mod. This implementation is not a
transactional backup system. It preflights every targeted directory, including
player progress, for paths outside the save and symbolic links before closing
worlds. A `hardcore_reset_in_progress` marker is written before erasure and removed
only after player recovery and a successful save. If an exception or process crash
interrupts this interval, the next normal server startup is refused.

If this marker remains, stop the server and restore a known-good world backup.
Alternatively, an administrator must inspect/recover all dimensions and player
state before manually removing the marker. Removing it alone does not repair an
interrupted reset. Other mods must not mutate these directories concurrently.

## Baseline diagnosis

The starting `port/26.2` commit referenced MinecraftServerAccessor,
ServerLevelAccessor, and PlayerAccessor in Java and Mixin configuration but omitted
their source files. Restoring them made 26.2 compile before changing versions.
Their target fields exist in both releases; the failure was not caused by 26.3.
The worldGenSettings setter requires `@Mutable` because the target field is final.

## Manual gameplay and compatibility checks

Automated players use embedded connections, not authenticated graphical clients.
Before release, test integrated singleplayer, real-client multiplayer packet/UI
behavior, disconnect/reconnect timing during each reset phase, countdown
cancellation across a server restart, custom datapacks/dimensions and optional
Trinkets installations. Authentication discovery still reports connection refusal
in this cloud environment, so authenticated multiplayer remains unverified.

No promise is made that arbitrary third-party mods tolerate replacing ServerLevel
instances: mods may retain world references or attach state outside vanilla save
directories. Test the intended modpack on a disposable copy. Custom dimension
retention is intentional and means those dimensions are not wiped.

The live cloud JDK/Gradle/dependency setup is verified. Persistence of a saved cloud
configuration into a fresh task remains unverified; the runtime reported no saved
configuration ID. Source `/workspace/work/java25-env.sh` in this current workspace.
